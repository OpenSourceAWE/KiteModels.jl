Introduction

Most of the functions work on a KPS3 or KPS4 object. For this, the variable s is used. Such a variable can be created with the lines:

using KiteSimulators
set = load_settings("system.yaml")
s = KPS3(KCU(set))

Or, if you want to use the 4 point kite model:

using KiteSimulators
set = load_settings("system.yaml")
s = KPS4(KCU(set))

Functions with an "!" as last character of the function name modify one of more of their parameters, in this context mostly the variable s.

KiteModels.set_v_wind_ground! — Function
set_v_wind_ground!(s::AKM, height, v_wind_gnd=s.set.v_wind; upwind_dir=-pi/2, interpolate=false)

Set the vector of the wind-velocity at the height of the kite. As parameter the height, the ground wind speed [m/s] and the upwind direction [radians] are needed. Is called by the function next_step!.

Both the mean and the turbulent wind come from calc_turbulent_wind, evaluated at the horizontal position of the kite and at height; interpolate is passed on to it. Since that function reads the ground wind speed from the settings, a v_wind_gnd differing from s.set.v_wind rescales the result; it has no effect while turbulence is switched on, where the wind field itself sets the speed.

s.v_wind_vert (set via the v_wind_vert keyword of next_step!, default 0.0) is added to the vertical component of s.v_wind after it is computed, on top of any vertical turbulence already present — it is a mean updraft/downdraft superimposed on the wind model, not a replacement for it. Positive is up. s.v_wind_gnd and s.v_wind_tether are unaffected: the tether wind stays horizontal, and upwind_dir (which reads s.v_wind_gnd) is unaffected too.

KiteModels.calc_turbulent_wind — Function
calc_turbulent_wind(am, pos, upwind_dir, t; interpolate=false)

Calculate the wind velocity vectors at the kite and at the mid-tether point.

When am.set.use_turbulence == 0.0, returns the mean wind based on a log/power-law height profile. When use_turbulence != 0.0, returns the fully turbulent wind vectors looked up from the pre-computed wind field via get_wind.

Forwards to AtmosphericModels.calc_turbulent_wind, which takes upwind_dir as a keyword argument; the positional argument order used here is kept for backwards compatibility.

Parameters:

  • am: atmospheric model (settings are read from am.set)
  • pos: 3D position of the kite [m]; pos[3] is used as height (clamped to 6 m minimum)
  • upwind_dir: upwind direction in radians; zero is north, clockwise positive
  • t: current simulation time [s]
  • interpolate: if true, interpolate the turbulence trilinearly between the surrounding grid points instead of using the nearest one

Returns a tuple (v_wind, v_wind_tether) where:

  • v_wind: wind velocity vector at kite height [m/s]
  • v_wind_tether: wind velocity vector at half the kite height [m/s]

KiteUtils.SysState — Type
SysState(s::AKM, zoom=1.0; with_springs=true)

Constructor for creating a SysState object from a kite model (KPS3 or KPS4). The SysState object can be used either for logging or for displaying the system state in a viewer. Optionally the position arrays can be zoomed according to the requirements of the viewer.

The field spring_force holds the forces of all springs (see spring_forces), or is empty if with_springs is false. The free fields var_13 and var_14 hold the internal state of the winch, the rate limited set speed wm.last_set_speed and the state of the brake wm.brake (0 or 1), so that init! can continue a simulation from the SysState; they are NaN without a winch model. A Logger for this SysState must be created with the same number of segments: Logger(P, steps; segments=n_springs(s)), or Logger(P, steps) with with_springs=false.

Saving the system state

The system state of one time step can be saved as human-readable YAML file, for example to inspect it or to compare two simulations. To log a whole simulation, use a Logger from KiteUtils instead.

KiteModels.save_state — Function
save_state(filename, ss::SysState; meta_data=Dict(), exclude=KiteModels.UNUSED_FIELDS)

Write the system state ss to the YAML file filename: the entries of the dictionary meta_data under the key meta_data, and the fields of ss under the key sys_state, except the fields in exclude, by default the fields that KPS3 and KPS4 do not use. For KPS3, pass exclude=KiteModels.UNUSED_FIELDS_KPS3 to also leave out side_slip, alpha3 and alpha4, which it does not have, and the aerodynamic moment aero_moment_KA_x/y/z, which is always zero. Scalars are written as numbers, vectors as YAML flow sequences, NaN and Inf as .nan and .inf, all other values as quoted strings. The keys of meta_data are written as strings, quoted unless they are plain identifiers.

Example:

ss = SysState(kps4)
save_state("output/sys_state.yaml", ss; meta_data=Dict("script" => "test_init_4p"))

The file can be read back with load_state.

KiteModels.load_state — Function
load_state(filename)

Read a system state from the YAML file filename that save_state wrote. Returns the tuple (sys_state, meta_data) of a new SysState and the Dict of the meta data.

The number of points and of springs of the SysState is taken from the length of the fields X and spring_force in the file. High level simulation interface

KiteUtils.init! — Function
init!(s::AKM; prn=false, steady_state=true, trim=false,
              initial_state=nothing) -> Union{OrdinaryDiffEqCore.ODEIntegrator, Sundials.IDAIntegrator, Nothing}

Initializes the integrator of the model (KPS3 and KPS4 only).

Parameters:

  • s: an instance of an abstract kite model
  • prn: if set to true, print the detailed solver results
  • steadystate: if true (default), call `findsteady_state!to solve for an equilibrium before constructing the integrator. Iffalse, skip the steady-state solver and initialise directly from the current model parameters viaKiteModels.init; this is faster but produces a non-equilibrium starting point, which is useful when the caller has already set up a consistent state or when the steady-state solver is known to struggle (e.g. unusual wind conditions). Returnsnothing` if steady-state solving fails.
  • trim: if true, the steady state is found at the natural elevation of the kite, where its lift matches gravity, instead of at s.set.elevation; see find_steady_state!. If no trim with attached flow is found, nothing is returned. Ignored if steady_state is false.
  • initialstate: a SysState to continue a simulation from, for example from [`loadstate](@ref). The model gets the positions and velocities of the particles, the tether length, the reel-out speed, the set values and the internal state of the winch and the depower and steering of the KCU from it, andsteadystateandtrimare ignored. The integrator continues atinitialstate.time, which must be the time of the state,integrator.twhen it was saved; aSysStatefromupdatesysstate!holds the start time of the last time step instead. For KPS4, the pitch rate of the kite is calculated from the velocities of the particles; it differs by O(dt) from the change of the pitch angle during the last time step, whichnext_step!` uses otherwise. The state of the controllers of the caller is not restored.

Without initial_state, the initial state is taken from the section initial of the settings; for KPS3 and KPS4 only the first value of each vector is used:

  • l_tethers, v_reel_outs and depowers: the tether length, the reel-out speed and the depower setting.
  • elevations: the elevation of the kite; with trim=true only the start value of the search for the natural elevation.
  • azimuths: the azimuth of the kite in the wind reference frame; see find_steady_state!.
  • steerings: the steering setting [%] of the KCU.
  • headings (KPS4 only): the heading of the kite. After the steady state was found, the kite is turned about the line from the KCU to the kite, which keeps the position of the kite and the lengths of all springs; the tether is not changed. A kite with a heading other than zero is not in equilibrium: it flies towards its nose. The one-point kite of KPS3 has no heading of its own, so the heading is ignored.
  • elevation_rates and azimuth_rates: the tether and the kite rotate as a rigid body about the winch, so that the elevation and the azimuth of the kite change with these rates [°/s].
  • heading_rates (KPS4 only): the kite also rotates about the line from the KCU to the kite, so that its heading changes with this rate [°/s]. The rates only set the velocities, not the accelerations, so the initial state is not consistent with them, which causes a transient during the first fraction of a second. For example, with an elevation rate of -5 °/s the tether force of KPS4 drops from 502 N to 48 N within 0.1 s. Without steering, the heading rate decays within about 0.1 s.
  • kite_distances is ignored.

The steady state is solved with the steering applied; its symmetric forces are balanced, but a steering other than zero makes the kite turn.

The keyword arguments delta and stiffness_factor are deprecated and ignored: with steady_state=true, the initial state is an equilibrium for the full tether stiffness.

Returns: An instance of an ODEIntegrator or IDAIntegrator, or nothing if initialization fails.

KiteModels.find_steady_state! — Function
find_steady_state!(s::KPS4; prn=false, upwind_dir=-pi/2, trim=false)

Find an initial equilibrium, based on the initial parameters l_tether, elevation, azimuth and v_reel_out.

The forces on the tether particles, the KCU and the kite particles are balanced (without gravity), except for the z component of the kite points C and D: instead, the elevation of the kite (pos_kite, point B) is kept at s.set.elevation, because the kite can only be fully balanced at its natural elevation. Therefore calc_elevation(s) returns s.set.elevation after the steady state was found. If the prescribed elevation is far below the natural elevation, the kite can only be balanced in deep stall, with an angle of attack beyond the angle of maximum lift; then a warning is logged.

The kite is placed at the azimuth s.set.azimuth (in degrees, in the wind reference frame). For an azimuth other than zero, the lateral forces on the tether particles are balanced too, but the lateral forces on the kite and the KCU are not: instead, the kite is kept at the prescribed azimuth. The kite is not in equilibrium there, it has a side slip angle, and without steering it swings back towards the azimuth zero.

If trim is true, all forces including gravity are balanced, also the z components of the forces on C and D, and the elevation is solved for instead: the kite is placed at the elevation where its lift matches gravity (its natural elevation), starting the search at 80° or at s.set.elevation, if it is higher: the solver converges from above the natural elevation, but often not from far below it. Trimmed steady states with an angle of attack beyond the angle of maximum lift (deep stall) are rejected. If no valid trim is found from the start elevation, the solver is restarted at higher and then at lower elevations than s.set.elevation, in steps of 10°. If this fails too, an error is thrown, and init! returns nothing.

The steady state is always solved for the full tether stiffness (s.stiffness_factor is 1.0 afterwards). The nonlinear solver is sensitive to the starting point, so small floating-point differences (e.g. between Julia versions) can decide whether it converges. If the first attempt fails, it is repeated without autoscaling and then by continuation: a solution is first found for a reduced tether stiffness and then used as start value for the full stiffness. The initial state is not perturbed, unless this fails; the returned steady state is never perturbed.

The keyword arguments delta and stiffness_factor are deprecated and ignored.

find_steady_state!(s::KPS3; prn=false, upwind_dir=-pi/2, trim=false)

Find an initial equilibrium, based on the initial parameters l_tether, elevation, azimuth and v_reel_out.

The tether particles are in equilibrium. The kite is placed at the elevation angle from the settings, so only its horizontal force balance is solved for; the kite can only be fully balanced at its natural elevation. If the prescribed elevation is far below the natural elevation, the kite can only be balanced in deep stall, with an angle of attack beyond the angle of maximum lift; then a warning is logged.

The kite is placed at the azimuth s.set.azimuth (in degrees, in the wind reference frame). For an azimuth other than zero, the lateral forces on the tether particles are balanced too, but the lateral forces on the kite are not: instead, the kite is kept at the prescribed azimuth. The kite is not in equilibrium there. Without a controller, the one-point kite is laterally unstable and moves further away from the azimuth zero.

If trim is true, the vertical force balance of the kite is solved for too and the elevation is free: the kite is placed at the elevation where its lift matches gravity (its natural elevation), starting the search at s.set.elevation. Trimmed steady states with an angle of attack beyond the angle of maximum lift (deep stall) are rejected. If no valid trim is found from s.set.elevation, the solver is restarted at higher and then at lower elevations, in steps of 10°. If this fails too, an error is thrown, and init! returns nothing.

The steady state is always solved for the full tether stiffness; a solution for a reduced stiffness is only used as start value. The keyword arguments delta and stiffness_factor are deprecated and ignored.
